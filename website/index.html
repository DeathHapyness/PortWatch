Visão geral

O que é o PortWatch?

PortWatch é uma plataforma open-source de monitoramento para homelabs que rodam cargas em Docker. Em quem confiar quando a pergunta é "que porta está livre?", "quem está publicando a 8080?" ou "quais containers caíram?"? O PortWatch responde isso ao vivo, sem banco de dados e sem jamais alterar o ambiente monitorado.

A plataforma combina duas fontes de verdade: a API do Docker (alcançada por um proxy de socket restrito a leitura) e uma sonda leve no namespace de rede do host. Um Collector, embutido no processo do backend, consulta essas fontes em ciclo contínuo e publica snapshots atômicos em memória. Sobre eles, uma API REST serve containers, redes, portas e um resumo do sistema — consumidos por um dashboard reativo.

🎯 Objetivo do projeto

Dar visibilidade completa e instantânea do estado de um homelab Docker — containers, portas e redes — com o mínimo de infraestrutura e o máximo de segurança.

🧭 Princípio central

Observar, nunca agir. Nenhum endpoint inicia, para ou reinicia containers. Estado é sempre rederivado ao vivo da realidade — nunca persistido nem presumido.

Por que ele existe

  • Saber qual porta está livre antes de publicar um novo serviço — sem sair caçando com netstat.
  • Ver quem publica o quê: o mapa completo entre portas do host e containers.
  • Detectar containers parados ou reiniciados num relance.
  • Entender a topologia de redes Docker do ambiente.
  • Zero risco: o único privilégio elevado fica confinado a componentes minúsculos e auditáveis.

Capacidades

O que o PortWatch faz

Tudo que a v1 entrega — cada dado derivado ao vivo das fontes, nunca persistido.

Descoberta de containers

Inventário ao vivo dos containers Docker: nome, imagem, status e detalhes por container — atualizado continuamente pelo Collector.

Visão unificada de portas

Cruzamento entre as portas publicadas pelos containers e as portas escutando no host: /api/v1/ports devolve a visão consolidada.

Portas livres no host

A sonda netprobe lê /proc/net/* do host e reporta portas ocupadas — o resto do range fica marcado como disponível (/ports/available).

Redes Docker

Listagem e detalhe das redes gerenciadas pelo Docker — bridges, overlays e a quais containers cada uma se conecta.

Resumo do sistema

Um endpoint de nível-dashboard (/system/summary) que condensa o estado global: containers, redes, portas e saúde do Collector.

Métricas Prometheus

Logs estruturados + endpoint de métricas para scrape do Prometheus do próprio usuário — séries temporais ficam na sua stack, não dentro do PortWatch.

Contrato

Backend FastAPI (Python 3.12) com spec OpenAPI automática em /openapi.json e documentação interativa em /docs. Todos os endpoints de dados são GET — a API não muta nada no ambiente.

Como funciona

Arquitetura com privilégio mínimo

Cada componente tem exatamente o acesso de que precisa — e nada mais. Nenhuma parte do PortWatch monta o socket Docker diretamente; nenhum componente além do netprobe usa rede do host.

host linux Docker Engine Fonte primária: containers, redes, eventos e info do daemon.
netns do host Pilhas de rede (/proc/net/*) Tabelas TCP/UDP do kernel — a verdade sobre portas escutando no host.
GET-only · :2375 docker-socket-proxy Único container com o socket Docker montado — e mesmo assim restrito a leitura de CONTAINERS, NETWORKS, INFO, EVENTS, VERSION.
network_mode: host · :8088 netprobe Sonda mínima que lê /proc/net/* do host. Sem nenhum acesso ao socket Docker.
processo único Backend — FastAPI + Collector O Collector consulta as duas sondas em background (lifespan do FastAPI) e publica snapshots atômicos em memória, com TTL curto invalidado por eventos. Sem IPC, sem fila, sem banco (ADR-0001, ADR-0002).
:8000 → :5173 Dashboard web React + TypeScript + Vite + TanStack Query + Recharts, consumindo a API via proxy /api/*.

No desenvolvimento, tudo roda contra um sandbox Docker isolado desta máquina (make dev-up), protegido por um guard que resolve o endpoint Docker uma única vez e recusa operar sobre qualquer daemon que não seja o Docker local de dev. Containers de teste carregam o label portwatch.env=dev-sandbox.

Segurança por desenho

Vigiar sem dar as chaves

Acesso ao socket Docker equivale a root no host. O PortWatch foi desenhado para nunca concentrar esse poder — cada decisão abaixo está registrada em um ADR.

Somente-observação

Nenhum endpoint inicia, para, reinicia ou executa comando em containers monitorados. Ações de mutação estão fora de escopo até decisão explícita que revisaria a ADR-0003.

Socket Docker atrás de proxy GET-only

O socket real só existe dentro do docker-socket-proxy, limitado a verbos de leitura. A aplicação conversa HTTP com ele — nunca monta /var/run/docker.sock (ADR-0003).

Privilégios separados por componente

O netprobe precisa ver a netns do host (network_mode: host) mas não enxerga o Docker. Todo o resto roda em rede normal e sem socket. O raio de dano de qualquer componente é mínimo.

Loopback por padrão + token fora dele

A API escuta em 127.0.0.1 por padrão; exposição em LAN/remoto é opt-in explícito e exige o token bearer estático da v1 (ADR-0004) — simples de auditar, sem contas nem OAuth.

Sandbox de dev com guard

Todo desenvolvimento acontece num compose isolado, com label de identificação e um guard.sh que valida o alvo antes de subir/derrubar — imune a TOCTOU e a contextos Docker errados.

Nada persistido

Sem banco na v1 (ADR-0002): o estado vive em memória e volta do Docker a cada ciclo. Reiniciar o PortWatch não perde dado algum — não há segunda fonte de verdade para divergir.
